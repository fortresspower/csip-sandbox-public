# Start here

**Fortress acts as the IEEE 2030.5 client. Your system hosts the IEEE 2030.5 server.**

Fortress initiates every request. You never call a Fortress endpoint, and you do not need
outbound access to Fortress for the polling integration. Getting this backwards is the single
most expensive mistake in a CSIP integration, so it is worth reading twice.

```text
demo → build your server → doctor → conformance → connect to Fortress
```

## Set up

```bash
npm install
npx fortress-csip help
```

That is the whole bootstrap. The toolkit binary is local to this checkout — `npm install`
builds it, and nothing is fetched from a registry when you run it.

## 1. See the loop work — `demo`

```bash
npx fortress-csip demo
```

Starts an example IEEE 2030.5 server and a mocked Fortress client on your machine, dispatching
and reporting against each other. No certificates, no Fortress account, no partner endpoint.

- Partner console: <http://localhost:7001/>
- Swagger UI: <http://localhost:7001/docs>
- Client status: <http://localhost:7100/status>

To prove the closed loop non-interactively — dispatch a bounded command and watch telemetry
move — and tear everything down afterwards:

```bash
npx fortress-csip demo --verify
```

To see the exact authorization decision Fortress will make, before any certificate has been
exchanged with anyone:

```bash
npx fortress-csip demo --mtls
```

This generates a disposable certificate authority, stands up the production-shaped partner app
behind a real TLS terminator, and proves four outcomes: a trusted and allowlisted client
succeeds, a client with no certificate fails, a client from an untrusted issuer fails, and a
trusted client whose LFDI is not allowlisted fails. All generated key material is removed when
it finishes, including on Ctrl-C.

Docker is required for `demo`, but not for `demo --mtls`.

## 2. Build your server

Read the [conformance profile](./conformance-profile.md) — the minimum contract your server
must meet — and use the example server in `packages/example-server` as a reference
implementation. The pieces worth copying are the composition seams: `PartnerPersistence` for
storage, and `ConnectionResolver` for deciding which connection a request belongs to.

Point the mocked Fortress client at your own server rather than the example one:

```bash
CSIP_SERVER_URL=http://host.docker.internal:8080 docker compose up client
```

## 3. Check readiness — `doctor`

```bash
npx fortress-csip doctor https://csip.your-company.example
```

Read-only. Every request is a `GET`; it never registers a device, publishes telemetry, creates
an assignment, or consumes a control, so it is safe against a live server.

Without a client certificate it runs the anonymous checks: origin, DNS, TLS, and — most
importantly — whether your server refuses a client that presents no identity at all. Anonymous
success is reported as a failure, because it means mutual TLS is not enforced.

With one, it also checks the certificate, the LFDI, whether that LFDI is authorized, and the
advertised resource graph:

```bash
npx fortress-csip doctor https://csip.your-company.example \
  --cert ./fortress-client.pem --key ./fortress-client.key
```

Against a loopback server with a private CA, use `--local`, which is the only mode that
accepts `--ca` or a non-443 port:

```bash
npx fortress-csip doctor https://localhost:8443 --local \
  --ca ./root.pem --cert ./client.pem --key ./client.key
```

## 4. Prove the profile — `conformance`

First prove the harness itself, which needs nothing but this checkout:

```bash
npx fortress-csip conformance --self-test
```

Then run it against your server:

```bash
npx fortress-csip conformance https://csip.your-company.example \
  --cert ./test-client.pem --key ./test-client.key \
  --out ./fortress-csip-evidence.json
```

Unlike `doctor`, this mutates: it registers two synthetic EndDevices, posts lifecycle
responses, and publishes telemetry. Every identity it uses is generated by the toolkit — no
real site identity is sent.

Two steps need your own operator tooling: assigning one test device to a DERProgram, and
publishing one bounded rehearsal control. The command prints exactly what to do and then
watches the connection. **Fortress does not require you to expose an administrative API**, and
this toolkit does not invent one.

The run is resumable, so pausing for an operator action does not force re-registration. See
[self-test and conformance](./self-test.md) for the full check list.

## 5. Hand off — `onboarding`

```bash
npx fortress-csip onboarding
npx fortress-csip onboarding --template --out ./fortress-csip-handoff.json
npx fortress-csip onboarding --validate ./fortress-csip-handoff.json
```

Send the validated submission and the evidence artifact through the agreed secure channel.
See [handoff](./handoff.md) for what happens next, and [operations](./operations.md) for
certificate rotation and day-two concerns.

## Answers to the questions people ask first

| Question | Answer |
|---|---|
| Who is the client? | Fortress. You host the server. |
| Which way does traffic flow? | Fortress → you, over HTTPS on TCP 443. |
| What does each side provide? | Run `fortress-csip onboarding`. |
| What is never exchanged? | Private keys, in either direction, and per-device rosters. |
| How do I run this locally? | `npx fortress-csip demo` |
| How do I test my server? | `fortress-csip doctor`, then `fortress-csip conformance`. |
| What do I send Fortress? | A validated handoff submission and the evidence artifact. |
| What happens before commands are enabled? | Discovery, enrollment, and telemetry with no control execution, then one bounded command rehearsal. |
| How does rotation avoid downtime? | Stage, preflight, promote, then remove the old identity. See [operations](./operations.md). |
